## 3. 設計の要点

- **I/O 契約**: CLI `nishiki diagnose` と Wasm `diagnose` は共通コア `run_diagnose` を呼ぶ。出力スキーマ `nishiki.diagnose/1`（6 レンズを固定順で常に出力、未実装は `unavailable`）。文字位置は元入力基準の Unicode スカラー値・半開区間。場面文字列は元入力の部分文字列と限らないため、場面分割の Rust 移植はオフセット対応を持つ。パリティはゴールデン JSON のバイト一致（ネイティブ・wasm32）。
- **検出器の Rust 移植仕様**: 3 量（語尾・読点・場面全体感覚語率）、作品内 LOO 経験ベイズ（m0 = 8）、校正済み片側分位スコア、K = 3 の max 集約、p_OP 最小 p 規則。Hurdle・2 部スコア・地の文限定・スパン長は移植から除外。正本が 1 パスの分散式を使うため同じ式で移植する。
- **分散安定化の選択**: ポアソン下側片側 p 値を暫定採用。根拠: 感覚語の個数は場面あたり平均 13.07（5 パーセンタイル 2、95 パーセンタイル 30）、個数 < 4 が 11.4%、場面長が 124〜1037 字（5〜95 パーセンタイル）で露出が不均一。Anscombe は小個数で近似が悪い。過分散（作品内 分散/平均 の中央値 4.44、場面長の変動を含む）のため p 値は過信になりうるが、後段の校正で吸収される見込み（未測定）。Anscombe を対照として P-4a で A/B し、事前登録規則で確定する。個数統計は地の文のみで、q3（場面全体）の個数ではない。
- **数値照合計画**: 数値のみのフィクスチャ（場面ごとの生量、fold 割当、中間量、`p_op` の全行）。許容誤差は Python 同士の再現性の底値 `ε_py` を実測し `max(100 × ε_py, 1e-12)`。閾値判定は完全一致を条件にする。
- **CI 下限の付随確認**: Python 先行（P-4a）。同一プロトコル（56 作品・1,877 場面、5 分割、seed 11、bootstrap B = 2000・seed 7）。未達なら Rust 移植に進まない。Rust 側では AUC 点推定の一致のみを条件にする。
- **盲検ハーネス**: `nishiki blind-run` / `blind-score`。評価者は不透明 ID・レンズ名なし・スコアなしのシートだけを見て先にマークし、`run.json` の SHA-256 を先に記録してから突き合わせる。場面単位の κ・感度・特異度、スパンは IoU を補助指標にする。原文・スパン内容はコミットしない。
