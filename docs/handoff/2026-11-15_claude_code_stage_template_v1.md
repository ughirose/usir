## 3. 判断規則（常設）

- **未定義の事項に出会った場合**: 自分で選択して進め、選択肢・採用案・理由を「選択表」としてレポートに載せる。ただし、選択が (a) 凍結成果物、(b) 公開 API・ファイル形式の契約、(c) Gate の合否、のいずれかを変える場合は進めず、§4 の STATUS に `state: blocked` と質問を 1 つ書いて push し、そのターンを終える。
- **このステージの変更に起因しない既存の失敗を見つけた場合**: 再現コマンドと出力の該当行を記録し、変更前コミットでも再現するかを 1 回確認して、続行する。修正はしない。
- **検証ゲートが未達の場合**: 条件を緩めない。未達のまま結論節の先頭に書く。
- 同じコマンド・テストが 2 回失敗したら同種の再試行をやめ、方針を変える。
- 指示に 1 対 1 で対応しない周辺コードの変更はしない。

## 4. 中間成果物と状態ファイル（常設）

- 最初の 10 分以内に、作業ブランチへ最初のコミットを push する。内容は `docs/handoff/STATUS_<stage-id>.md` と、その時点の作業途中のコードでよい（コミットメッセージは `wip(<id>): ...`）。
- 以後、タスク完了ごとに commit・push する。1 つのタスクが 15 分を超える場合は、タスクの途中でも `wip` コミットを push する。
- `STATUS_<stage-id>.md` は次の形式で、push のたびに更新する。

```
stage: <ID>
state: running | blocked | done
updated: <YYYY-MM-DD HH:MM JST>
branch: <作業ブランチ>
last_commit: <hash>
tasks: T1 done / T2 running / T3 todo ...
next: <次の 1 手>
question: <blocked のときだけ。1 つ>
```

- 使用量の上限などで中断した場合に備え、未コミットの変更を 15 分以上持たない。再開の指示を受けたら、STATUS と `git status` を読んで続きから始める。

## 7. レポート要件と完了条件（常設）

レポート `docs/handoff/<YYYY-MM-DD>_<project>_stage_<id>_report.md` に次の節を、この順で置く。

1. **結論**: 完了条件ごとに 達成／未達 と実測値。未達を先に書く。
2. **作業ブランチとコミット一覧**: ハッシュと 1 行説明。取り込み方法（ff 可否）。
3. **実装・計測の内容**
4. **検証ゲート結果**: §6 の表に実測値を入れたもの。
5. **選択表**: 未定義事項について自分で選んだもの（§3）。
6. **プロンプト・仕様書との食い違い**
7. **未検証・限界**: 実施していない検証、合成データだけで確認した点、CI で走らない検証。推測は「推測」と書く。
8. **自己批判的監査**: 次の 3 問に各 1 項目以上で答える。(a) この結果が誤りだとしたら、最も疑わしい箇所はどこか。(b) 通過したゲートのうち、欠陥があっても通過してしまうものはどれか。(c) 次のステージが誤解しそうな記述はどれか。
9. **申し送り**: `docs/handoff/OPEN_ITEMS.md` に追記した項目とクローズした項目。形式は `- [ ] <ID>-<n> <内容>（出所: <レポート名 §節>、種別: 未検証｜副作用｜判断待ち）`。
10. **対象外（実施していないこと）**
11. **進捗と NEXT**: 各 1 行。

完了条件:

- レポート、evidence、`OPEN_ITEMS.md` の更新、`STATUS_<stage-id>.md`（`state: done`）が作業ブランチに push 済みであること。**これが完了信号**。
- リモートコントロール方式では、加えてレポートを `F:\マイドライブ\Claude-Sync\inbox\` に複製する。クラウド方式では複製しない（できない）ことをレポートに 1 行書く。
- 作業ブランチと worktree は残す。削除はしない。
- 完了報告（チャット）は、結論 3 行、作業ブランチ名、最終コミット、未達・判断待ちの有無だけにする。

| 条件 | 割り当て |

| §5 に未確定項目が 3 つ以上残る | 先に仕様確定ステージ（調査・設計レーン）を切り、実装は Sonnet |

Fable の運用制約（F7 §2.2、§4.1 の実測に基づく）:

- 同時に走らせる Fable セッションは 1 本。
- 1 つの 5 時間窓に Fable のステージは 1 つ。窓の先頭（リセット直後）に投入する。
- Fable セッションに取り込みをさせない。取り込みは別の Sonnet セッションで行う。
- 実測では、Fable の 1 ステージは出力 8 万〜16 万トークン、上限到達は直前 5 時間の出力 12 万〜20 万トークンで起きた。この範囲は観測値で、仕様値ではない。

## 付録 C：取り込み用の定型プロンプト（Sonnet）

```
# <プロジェクト> Stage <ID> の取り込み（ユーザー承認済み）

対象: メインクローン <path>、本流 <branch>、取り込むブランチ <stage branch>（最終コミット <hash>）。

1. メインクローンで git fetch。本流がクリーンであることを確認（未追跡・未コミットがあれば一覧を記録し、触らない）。
2. git merge --ff-only <stage branch>。ff できない場合は何もせず、理由を報告して終了。
3. 取り込み後にメインクローンで実行し、件数を記録:
   - <cargo test --workspace --exclude kasane-wasm>
   - <環境変数つき検証（USIR_DATA_DIR=...）>
   - <python scripts/harness.py test>、<node --test ...>
   - 凍結成果物の SHA-256 照合（一覧の正本 <path>）
4. 全件通過なら git push。1 つでも失敗したら push せず、失敗出力の該当行を報告して終了（マージは戻さない。判断を仰ぐ）。
5. マージノート docs/handoff/<date>_<project>_stage_<id>_merge_note.md を作成し commit・push、inbox に複製:
   取り込み結果（前後のハッシュ）／テスト結果（件数）／実行しなかった検証と理由／OPEN_ITEMS の変化／
   作業ブランチと worktree の削除可否（削除はしない。「削除可」か「残す理由」を書く）。
6. STATUS_<stage-id>.md に merged: <hash> を追記。
```
